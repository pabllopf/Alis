## Analysis

GameWindow constructors delegate to NativeWindow constructors that create a
GLFW window. On macOS, GLFW requires initialization and window creation on the
process main thread. The repo's own bootstrap (StartupHook + GlfwTestBootstrap +
MainThreadNativeWorker) runs them on the main thread via DOTNET_STARTUP_HOOKS
with ALIS_GLFW_HOOK=1. Without those env vars the execution tests are documented
no-ops, so the constructors never run.

Attempting to construct GameWindow on an xUnit worker thread without GLFW init
is not viable: glfwCreateWindow hangs the process (verified empirically; a
candidate test was written and removed). The correct approach is the repo's
startup hook.

The hook initially failed because the test assembly's generated Memory module
initializer cannot resolve Alis.Core.Aspect.Memory during the startup-hook
phase. A temporary preload hook (built outside the repo, in
/var/folders/.../opencode/glfwpreload) preloads the Alis.* assemblies from the
test output before the test hook runs, making the module initializer succeed.
With the hook active, GameWindowExecutionTests actually run and the OpenCover
report shows GameWindow.cs at 10/10 sequence points.
